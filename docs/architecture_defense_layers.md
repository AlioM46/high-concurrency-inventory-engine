# هندسة طبقات الحماية المتعددة (Defense-in-Depth Architecture)

في الأنظمة الموزعة عالية التزامن (High-Concurrency Distributed Systems) لتجارة التجزئة وحجز التذاكر، لا يمكن الاعتماد على نقطة حماية واحدة لحفظ سلامة المخزون والبيانات المالية.

تعتمد منصة **StockForge** مبدأ **"القلعة متعددة الأسوار" (Layered Defense)**؛ حيث تتوزع المسؤوليات بدقة متناهية وفق مبدأ المسؤولية الواحدة (**Single Responsibility Principle**)، بحيث يؤدي كل كلاس ومكون دوره المتخصص دون تداخل أو فوضى برمجية.

---

## 1. خريطة طبقات الحماية (Architectural Flow)

```
[ العميل / متصفح الويب / تطبيق الموبايل ]
                   │
                   ▼
┌─────────────────────────────────────────────────────────────┐
│ السور 1: بوابة الـ API (Edge & Replay Protection)           │
│ المكون: IdempotencyMiddleware                               │
│ التهديد المصدود: تكرار النقرات وانقطاع الشبكة (Replay)      │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ السور 2: منسق الحجز وسلة المشتريات (Orchestration Layer)   │
│ المكون: ReservationService                                  │
│ التهديد المصدود: التعليق المتبادل (Deadlock) في السلات       │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ السور 3: دفتر الأستاذ المحاسبي (Double-Entry Ledger)         │
│ المكون: StockMovementService                                │
│ التهديد المصدود: البيع الزائد (Overselling) والـ Race Cond   │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ السور 4: محرك قاعدة البيانات الصلب (Storage Engine)         │
│ المكون: PostgreSQL Check Constraints & Indexes              │
│ التهديد المصدود: أخطاء المطورين وأوامر SQL المباشرة         │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ السور 5: صمام أمان الدفع والمؤقتات (Asynchronous Security)   │
│ المكون: ExpireReservationJob + StripeWebhookController      │
│ التهديد المصدود: تعارض الدفع مع انتهاء الوقت (Race vs Expiry)│
└─────────────────────────────────────────────────────────────┘
```

## 2. تفصيل الطبقات الخمس ومسؤولياتها

### السور الأول: بوابة الـ API والشبكة (`IdempotencyMiddleware`)
- **الملف المسؤول:** `app/Http/Middleware/IdempotencyMiddleware.php`
- **ماذا يحمي؟** خوادم التطبيق وقاعدة البيانات من تلقي نفس الطلب أكثر من مرة.
- **سيناريو التهديد:** 
  عميل ضغط زر "حجز" عدة مرات بسرعة بسبب بطء جهازه، أو انقطع اتصال 4G فأعاد المتصفح إرسال الطلب تلقائياً.
- **آلية العمل والحماية:**
  1. يجبر العميل على إرسال ترويسة `Idempotency-Key: <UUID>`.
  2. يقوم الميدلوير بعمل هاش تشفيري لمحتوى الطلب (SHA-256 Request Payload Hash).
  3. يفحص الـ Key في **Redis** ككاش فائق السرعة، وفي جدول `idempotency_keys` في PostgreSQL.
  4. إذا وصل نفس المفتاح مرة أخرى: **لا يمرر الطلب نهائياً لأي سيرفس داخلية**، بل يعيد نفس النتيجة السابقة المخزنة مباشرة (Cached Response).

---

### السور الثاني: منسق سلة المشتريات (`ReservationService`)
- **الملف المسؤول:** `app/Services/ReservationService.php` (مع استراتيجيات Concurrency Strategy A & B)
- **ماذا يحمي؟** حماية العمليات التي تشمل عدة منتجات في سلة واحدة من الانهيار والتعليق.
- **سيناريو التهديد:** 
  - العميل (أحمد) يشتري: `[لابتوب، جوال]`
  - العميل (خالد) يشتري: `[جوال، لابتوب]`
  - كلاهما يقفل منتجاً وينتظر الآخر فيحدث تعليق دائم (**Deadlock**).
- **آلية العمل والحماية:**
  - **الترتيب الحتمي للموارد (Deterministic Resource Sorting):**
    يقوم الكلاس بفرز المعرفات أبجدياً دائماً (`sort($productWarehouseIds)`) قبل طلب قفلها.
  - بهذا يتوحد مسار كل العمليات في قاعدة البيانات، ويستحيل رياضياً تشكل حلقة انتظار متبادل (Circular Wait).
  - كما يضمن مبدأ الذرية (**Atomicity**): إما تُحجز كل منتجات السلة أو تفشل كلها، فلا يخرج عميل بحجز جزئي غير مرغوب.

---

### السور الثالث: دفتر الأستاذ المحاسبي المزدوج (`StockMovementService`)
- **الملف المسؤول:** `app/Services/StockMovementService.php`
- **ماذا يحمي؟** رصيد المستودع الفعلي في جدول `product_warehouses` من أي تضارب تزامني، وتوثيق سجل محاسبي غير قابل للتعديل.
- **سيناريو التهديد:** 
  مئات المستخدمين يطلبون آخر 5 قطع متبقية في نفس جزء الألف من الثانية، أو أمين مستودع يورد بضاعة بالتزامن مع حجز زبون.
- **آلية العمل والحماية:**
  1. يقفل الصف الفردي فورياً في PostgreSQL عبر `SELECT ... FOR UPDATE` لمنع القراءات المتقادمة (Stale Reads).
  2. يفحص توفر المخزون الحقيقي على الصف المقفول حصرياً.
  3. يحدّث العدادات ويزيد رقم النسخة (`version++`).
  4. يسجل حركة محاسبية ثابتة لا تحذف أبداً في `stock_movements` (حساب مدين ودائن).

---

### السور الرابع: الحصن الفيزيائي لقاعدة البيانات (`PostgreSQL Storage Engine`)
- **الملف المسؤول:** المايجريشنز في `database/migrations/`
- **ماذا يحمي؟** سلامة البيانات من أي أخطاء بشرية من المطورين أو استعلامات SQL يدوية خاطئة.
- **سيناريو التهديد:** 
  مطور جديد كتب كوداً غير محمي، أو تم تنفيذ أمر صيانة يدوي بالخطأ يحاول جعل المخزون سالباً.
- **آلية العمل والحماية:**
  - قيد فحص فيزيائي على مستوى الجدول:
    ```sql
    ALTER TABLE product_warehouses 
    ADD CONSTRAINT chk_available_quantity_non_negative 
    CHECK (available_quantity >= 0);
    ```
  - حتى لو انهار كود لارفيل بالكامل، يرفض محرك PostgreSQL على مستوى القرص الصلب كتابة أي رقم سالب، ويرمي استثناء `QueryException`.

---

### السور الخامس: صمام أمان التعاملات غير المتزامنة والدفع (`Async & Payment Webhooks`)
- **الملفات المسؤولة:** `app/Jobs/ExpireReservationJob.php` و `app/Http/Controllers/Api/V1/WebhookController.php`
- **ماذا يحمي؟** حماية المخزون من التعليق الأبدي (Abandoned Carts)، وحماية أموال العميل عند تعارض وقت الدفع.
- **سيناريو التهديد:** 
  عميل حجز قطعة وترك جهازه دون دفع، أو عميل دفع في Stripe بعد الدقيقة 10 (بعد أن تم فك الحجز وبيعت القطعة لشخص آخر).
- **آلية العمل والحماية:**
  1. **مؤقت الإلغاء (10-Minute TTL):**
     يُرسل جوب مؤجل في Redis لمدة 10 دقائق؛ إذا لم يتم الدفع، يُعاد المخزون تلقائياً إلى الرصيد المتاح عبر `recordRelease`.
  2. **حارس الدفع المتأخر (Atomic State Compare & Refund):**
     عند وصول إشعار الدفع من Stripe:
     - إذا كان الحجز ما زال نشطاً (`ACTIVE`): يُحول فوراً إلى طلب مدفوع (`recordSale`).
     - إذا كان الحجز قد انتهى (`EXPIRED`) ونفد المخزون: يُطلق النظام فوراً أمر استرجاع مالي آلي (**Automated Refund**) عبر Stripe API لحماية حق العميل دون أي تدخل بشري.

## 3. جدول مصفوفة التهديدات وطبقات المعالجة (Threat Matrix)

| نوع التهديد (Threat) | السور المسؤول (Defending Layer) | الكلاس / المكون المسؤول | النتيجة المحققة |
| :--- | :--- | :--- | :--- |
| **تكرار النقرات والشبكة** | السور الأول (HTTP Edge) | `IdempotencyMiddleware` | منع التكرار وإرجاع كاش فوري |
| **التعليق المتبادل (Deadlock)** | السور الثاني (Orchestrator) | `ReservationService` | ترتيب أبجدي حتمي للمنتجات |
| **البيع الزائد (Overselling)** | السور الثالث (Ledger) | `StockMovementService` | قفل تشاؤمي على مستوى الصف |
| **أخطاء المطورين / SQL** | السور الرابع (Database) | `PostgreSQL CHECK Constraint` | استحالة فيزيائية لنزول المخزون عن الصفر |
| **السلات المتروكة (Abandoned)** | السور الخامس (Async TTL) | `ExpireReservationJob` (Redis) | إرجاع المخزون المتاح بعد 10 دقائق |
| **الدفع بعد انتهاء المهلة** | السور الخامس (Payment Hook) | `WebhookController` | استرجاع مالي آلي (Auto Refund) |
