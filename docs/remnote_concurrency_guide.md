# دليل هندسة التزامن والأنظمة الموزعة (StockForge)
# High-Concurrency & Distributed Backend Engineering Guide
*مهيأ للتصدير والمراجعة عبر RemNote (يدعم البطاقات التعليمية Flashcards بصيغة `::`)*

## 1. أساسيات البنية التحتية (Infrastructure Fundamentals)

- **دوكر (Docker)** :: تقنية تتيح تشغيل البرامج وقواعد البيانات داخل "حاويات معزولة وموحدة" (Containers)، مما يضمن تشغيل الكود بنفس الطريقة تماماً على أي جهاز أو خادم دون مشاكل اختلاف البيئات.
  - **الصورة (Image)** :: هي "القرص الجاهز" أو المخطط غير القابل للتعديل الذي يحتوي على نظام التشغيل المصغر والبرنامج (مثل صورة `postgres:16-alpine`).
  - **الحاوية (Container)** :: هي النسخة الحية التي تعمل حالياً على جهازك انطلاقاً من تلك الصورة.
  - **المساحة التخزينية (Volume)** :: هي بمثابة "فلاش ميموري" خارجي متصل بالحاوية لحفظ بيانات قاعدة البيانات على القرص الحقيقي حتى لا تضيع عند إطفاء الحاوية أو حذفها.

- **ملف `docker-compose.yml`** :: ملف نصي موحد يعمل كـ "مايسترو" لإدارة وتشغيل عدة حاويات مرتبطة ببعضها (مثل PostgreSQL + Redis) بأمر واحد (`docker compose up -d`) بدلاً من كتابة أوامر تشغيل يدوية طويلة ومعقدة.

- **خادم Redis** :: قاعدة بيانات فائقة السرعة تعمل بالكامل في الذاكرة الحية (RAM) بنظام المفتاح والقيمة (Key-Value)، وتستطيع معالجة مئات آلاف العمليات في أجزاء من الميكروثانية.
  - **لماذا لا نكتفي بـ PostgreSQL؟** :: لأن PostgreSQL تخزن على القرص الصلب (Hard Disk/SSD) لضمان الأمان الدائم، وتعتبر بطيئة جداً ومكلفة لو استخدمناها في المهام اللحظية السريعة.
  - **الاستخدام 1 في مشروعنا: طوابير المهام المؤجلة (Delayed Queues)** :: تخزين تذكرة لإلغاء الحجز تلقائياً بعد 10 دقائق بالضبط دون إشغال المعالج أو تعليق طلب المستخدم بـ `sleep()`.
  - **الاستخدام 2 في مشروعنا: استلام إشعارات الدفع (Webhooks Queue)** :: الرد الفوري على بوابة Stripe (HTTP 200) وتخزين الإشعار في طابور لمعالجته في الخلفية دون تأخير.
  - **الاستخدام 3 في مشروعنا: كاش الـ Idempotency** :: فحص مفاتيح التكرار في أجزاء من الميلي ثانية لمنع الضغطات المزدوجة قبل أن تلمس قاعدة البيانات.

- **الـ Webhook** :: آلية ترسل بها منصة خارجية (مثل Stripe) رسالة HTTP أوتوماتيكية إلى سيرفرنا فور وقوع حدث معين (مثل نجاح خصم أموال العميل) بدلاً من استنزاف السيرفر بالسؤال الدوري المتكرر (Polling).

## 2. معضلات التزامن الكبرى وحلولها الهندسية (Concurrency Control)

- **سباق التزامن (Race Condition)** :: خلل هندسي خطير يحدث عندما يطلب عميلان تعديل نفس البيانات في نفس الجزء من الثانية، فتقرأ العمليتان نفس القيمة القديمة قبل أن يُسجل تعديل الأولى، مما يؤدي إلى نتائج كارثية مثل بيع مخزون غير موجود (Overselling).

- **القفل المتشائم (Pessimistic Locking - `lockForUpdate`)** ::
  - **المفهوم** :: قفل صف قاعدة البيانات بالمفتاح أثناء وجودك داخل Transaction في PHP، ومنع أي استعلام آخر من قراءته أو تعديله حتى تنتهي.
  - **أين يتم المنطق؟** :: داخل كود الـ Backend (Laravel/PHP).
  - **مدة القفل** :: طويلة نسبياً (20 إلى 50 ميلي ثانية) لأن القفل يبقى مفتوحاً طوال فترة تنفيذ خطوات PHP.
  - **الميزة** :: يمنحك راحة تامة في إجراء حسابات وشروط عمل معقدة جداً قبل الحجز.
  - **العيب** :: تحت الضغط العالي (Flash Sale)، تتراكم الطلبات في طابور طويل وتختنق اتصالات قاعدة البيانات (Lock Contention).

- **التحديث الذري المشروط (Atomic Conditional Update)** ::
  - **المفهوم** :: دمج شرط الفحص وعملية التعديل في استعلام SQL واحد لا يقبل التجزئة داخل محرك قاعدة البيانات نفسه:
    ```sql
    UPDATE inventories 
    SET available_quantity = available_quantity - 1,
        reserved_quantity = reserved_quantity + 1 
    WHERE id = :id AND available_quantity >= :qty;
    ```
  - **أين يتم المنطق؟** :: داخل محرك PostgreSQL الداخلي، دون وساطة PHP.
  - **مدة القفل** :: بالغة الصغر (أجزاء من الميكروثانية).
  - **كيف يمنع الـ Race Condition؟** :: محرك PostgreSQL فيزيائياً لا يستطيع تعديل نفس البايت في نفس اللحظة؛ فيعالج طلباً ويخصم ويحول القيمة إلى `0`، وعندما يدخل الطلب التالي يعيد محرك Postgres فحص شرط `WHERE available >= 1` فيجده خاطئاً ويرفض التعديل فوراً (`0 rows updated`).
  - **الميزة** :: سرعة خارقة وإنتاجية هائلة (Throughput) تحت آلاف الطلبات المتزامنة.

- **المأزق الحرج (Deadlock)** ::
  - **المفهوم** :: حالة تجمد وشلل تام في قاعدة البيانات تحدث عندما تمسك العملية الأولى قفل السلعة A وتنتظر السلعة B، بينما تمسك العملية الثانية قفل السلعة B وتنتظر السلعة A.
  - **قانون الحل (Deterministic Lock Sorting)** :: إجبار جميع عمليات النظام على قفل السلع دائماً بالترتيب التصاعدي لأرقامها (`ORDER BY product_id ASC`). هذا يكسر حلقة الانتظار الدائري (Circular Wait) ويمنع الـ Deadlock نهائياً.

- **حماية التكرار (Idempotency)** ::
  - **المفهوم** :: ميزة برمجية تضمن أن تكرار إرسال نفس الطلب عدة مرات (بسبب بطء الإنترنت أو نقر العميل المتوتر لزر الشراء 5 مرات متتالية) ينتج عنه نفس النتيجة الأولى بالضبط دون تكرار الخصم أو تكرار الحجز.
  - **كيف تعمل؟** :: العميل يرسل ترويسة `Idempotency-Key: uuid` مع الطلب؛ السيرفر يخزن نتيجة العملية الأولى، وإذا تكرر نفس الـ Key يعيد له النتيجة المخزنة فوراً دون لمس المخزون مجدداً.

## 3. مقارنة المفاهيم الهندسية الأربعة (Master Summary Table)

| المفهوم الهندسي | ما هو؟ | ما المشكلة التي يحلها؟ | أين يقع تنفيذه؟ |
| :--- | :--- | :--- | :--- |
| **Pessimistic Locking** | قفل الصف عبر `lockForUpdate()` | يمنع الـ Race Condition للمنطق المعقد | داخل كود PHP عبر Database Transaction |
| **Atomic Update** | استعلام SQL شرطي واحد مدمج | يمنع الـ Race Condition بأعلى سرعة ممكنة | داخل محرك PostgreSQL الداخلي |
| **Deadlock Prevention** | ترتيب قفل العناصر تصاعدياً (`ORDER BY id`) | يمنع الشلل وتجمد السيرفر عند حجز عدة عناصر | في ترتيب استعلامات الـ SQL |
| **Idempotency** | استخدام ترويسة `Idempotency-Key` | يمنع تكرار الحجز أو سحب الأموال عند تكرار النقرات | في طبقة الـ API Middleware وكاش Redis |

## 4. دورات الحياة الثلاثية وتكامل المدفوعات (Lifecycles & State Machines)

- **لماذا نفصل الحجز عن الطلب عن الدفع؟** :: لتحقيق مبدأ المسؤولية الفردية (Decoupling)؛ فلو فشلت البطاقة الأولى للعميل لا يخسر مقعده أو حجز سلعته، بل يظل الحجز نشطاً ويستطيع إدخال بطاقة ثانية بهدوء.

- **1. دورة حياة الحجز (Reservation FSM)** ::
  - تهتم بـ: **المخزن والقطع الفعلية**.
  - عمرها: **قصير جداً (10 دقائق)**.
  - الحالات: `ACTIVE` $\rightarrow$ (`CONFIRMED` عند الدفع | `EXPIRED` عند انتهاء الوقت | `RELEASED` عند الإلغاء اليدوي).
  - معادلة المخزون: $\text{Total} = \text{Available} + \text{Reserved} + \text{Sold}$.

- **2. دورة حياة الطلب (Order FSM)** ::
  - تهتم بـ: **العقد التجاري والأسعار والعناوين والفاتورة القانونية**.
  - عمرها: **دائم**.
  - الحالات: `PENDING_PAYMENT` $\rightarrow$ (`PAID` | `PAYMENT_FAILED` | `EXPIRED` | `CANCELLED`).

- **3. دورة حياة الدفع (Payment FSM)** ::
  - تهتم بـ: **العملية المالية البنكية ورقم العملية في Stripe**.
  - عمرها: **لحظي مع إمكانية الاسترداد لاحقاً**.
  - الحالات: `PENDING` $\rightarrow$ (`SUCCEEDED` | `FAILED` | `REFUNDED`).

- **معضلة سباق انتهاء الحجز مع وصول الدفع (Expiry vs. Payment Race)** ::
  - **السيناريو** :: في الدقيقة 10:00:00 انتهت مهلة الحجز وأطلق الـ Worker أمر إعادة السلعة للمخزن واشتراها شخص آخر، وفي الدقيقة 10:00:01 وصل إشعار Stripe بأن العميل دفع في اللحظة الأخيرة!
  - **الحل بالاستعلام الذري** ::
    ```sql
    UPDATE reservations SET status = 'CONFIRMED' WHERE id = :id AND status = 'ACTIVE';
    ```
    يفشل الاستعلام ويعيد `0 rows updated` لأن الحالة لم تعد `ACTIVE`، فيدرك النظام فوراً وقوع حالة السباق، ويُطلق تلقائياً أمر استرداد فوري للأموال (**Automatic Stripe Refund**) مع إشعار اعتذار للعميل.

## 5. بطاقات للمراجعة السريعة في RemNote (Flashcards)

- ما هو المبدأ الأساسي للعملية الذرية (Atomic Operation)؟ :: إما أن تكتمل العملية بكافة خطواتها بنجاح 100%، أو تُلغى بالكامل دون ترك أي أثر نصفي (All or Nothing).
- ما الفرق بين الـ Deadlock والـ Idempotency؟ :: الـ Deadlock هو تجمد لقاعدة البيانات بسبب انتظار متبادل بين معاملتين، بينما الـ Idempotency هي تقنية لمنع تكرار معالجة الطلب نفسه عند تكرار إرساله من العميل.
- ما هي الحالات الثلاث لحسابات المخزون في StockForge؟ :: المتاح للحجز (Available)، والمحجوز مؤقتاً (Reserved)، والمباع نهائياً (Sold).
- لماذا نستخدم الترتيب التصاعدي `ORDER BY product_id ASC` عند قفل عناصر السلة؟ :: لكسر حلقة الانتظار الدائري وضمان أن جميع العمليات المتزامنة تقفل نفس العناصر بنفس الترتيب، مما يمنع الـ Deadlock تماماً.
- ما التصرف السليم إذا نجح دفع العميل بعد أن انتهت صلاحية حجزه وبيعت السلعة لغيره؟ :: رفض تأكيد الحجز وإطلاق استرداد مالي تلقائي فوري (Auto Refund) عبر بوابة الدفع.
